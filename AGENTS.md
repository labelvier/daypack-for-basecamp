# Development Guidelines for Basecamp Kanban Filter

> See [CHANGELOG.md](./CHANGELOG.md) for a history of notable changes.

## Project Overview

Browser extension (Chrome, Firefox + Safari) that adds filtering capabilities to Basecamp 4 card tables (kanban boards). The extension runs as a content script on Basecamp pages, adding assignee, author, and tag filters with visual tag pills.

## Build & Development Commands

### Setup (after cloning)

```bash
npm install
npm run build
```

### Development (with file watcher)

```bash
npm run dev
```

Watches the entire `shared/` directory tree (all `.js` and `.css` files). On every save:
1. Rebuilds (readable + inline sourcemaps) into `chrome/shared/`, `firefox/shared/` and `safari/.../Resources/`
2. Prints a reminder to reload the extension in Chrome

**To reload the extension after a build:**
- Chrome: go to `chrome://extensions`, click the **↺ reload** button on Daypack by Label Vier
- Firefox: go to `about:debugging#/runtime/this-firefox`, click the **Reload** button on Daypack by Label Vier
- Safari: rebuild in Xcode (⌘R) — Xcode picks up the new files automatically

### Production Build

```bash
npm run build
```

Minifies JS (~20 kB, down from ~52 kB) and CSS into `chrome/shared/`, `firefox/shared/` and `safari/.../Resources/`.

### Package Chrome Extension

```bash
npm run package:chrome
```

Runs a production build, then zips `chrome/` → `build/chrome/daypack-by-label-vier-chrome-v{version}.zip`.
Upload that file to the Chrome Web Store.

### Package Firefox Extension

```bash
npm run package:firefox
```

Runs a production build, then zips `firefox/` → `build/firefox/daypack-by-label-vier-firefox-v{version}.zip`.
Upload that file to Firefox Add-ons (AMO).

### Package Safari Extension

```bash
npm run package:safari
```

Runs a production build, then `xcodebuild -configuration Release` and zips the resulting `.app` → `build/safari/daypack-by-label-vier-safari-v{version}.zip`. macOS + Xcode required.

The `.app` is signed with whatever signing identity Xcode picks (typically Development). Suitable for distribution outside the App Store and for the GitHub release attachment. **For App Store submission**, open the project in Xcode → Product → Archive → Distribute → App Store Connect.

## File Synchronization Strategy

### ⚠ Build — Do Not Edit Generated Files

`content.js` and `content.css` in `chrome/shared/`, `firefox/shared/` and `safari/.../Resources/` are **generated by the build script**. They are git-ignored and will be overwritten on the next build.

**Always edit only in `/shared/`.**

| Location | Status |
|---|---|
| `shared/content.js` | ✅ Source of truth — edit here |
| `shared/content.css` | ✅ Source of truth — edit here |
| `chrome/shared/content.js` | ⚠ Generated — do not edit |
| `chrome/shared/content.css` | ⚠ Generated — do not edit |
| `firefox/shared/content.js` | ⚠ Generated — do not edit |
| `firefox/shared/content.css` | ⚠ Generated — do not edit |
| `safari/.../Resources/content.js` | ⚠ Generated — do not edit |
| `safari/.../Resources/content.css` | ⚠ Generated — do not edit |

### After `git pull`

Always run `npm install && npm run build` after pulling to regenerate the output files.

## Always commit

After implementing a change, commit both the source files in `shared/` but ignore generated files in `chrome/shared/`, `firefox/shared/` and `safari/.../Resources/`. This prevents merge conflicts and ensures the build output is always reproducible from the source.

## Ask for updates for changelog

When you make changes, ask if you need to update the [CHANGELOG.md](./CHANGELOG.md) with a brief description of the change, the version number, and the date. This helps keep track of what has been changed and when.

## Releasing a new version

When creating a release (minor or major), follow these steps:

1. Bump the version in `package.json`, `chrome/manifest.json` and `firefox/manifest.json`
2. Update `CHANGELOG.md` — move items from `[Unreleased]` into a new dated section
3. Commit all changes with message: `chore: bump version to x.y.z`
4. Push to `main`
5. Create a GitHub release using the `gh` CLI:
   ```bash
   gh release create vx.y.z --title "vx.y.z" --notes "..." --latest
   ```
   Use the CHANGELOG entry for that version as the release notes.
6. The `Release` workflow (`.github/workflows/release.yml`) auto-runs:
   - **`validate` job** runs first and fails the entire release if `CHANGELOG.md` has no populated entry for the release tag (via `npm run check:changelog`). All deploy jobs declare `needs: validate`, so a missing changelog blocks the upload.
   - Builds Chrome + Firefox + Safari zips and attaches them to the GitHub release
   - Uploads + publishes to Chrome Web Store (via `chrome-webstore-upload`)
   - Signs + uploads to Firefox AMO (via `web-ext sign`)
   - Safari `.app` (built on a `macos-latest` runner) is only attached to the GitHub release; App Store submission still requires Xcode → Archive locally

The local `deploy:chrome` and `deploy:firefox` scripts run the same changelog check before uploading anything.

### Required GitHub repo secrets

For auto-deploy to work, set these secrets in **Settings → Secrets and variables → Actions**:

| Secret | Where to get it |
|---|---|
| `CHROME_EXTENSION_ID` | Chrome Web Store Dev Console → extension page (URL contains the ID) |
| `CHROME_CLIENT_ID` | Google Cloud Console → OAuth 2.0 client ID for Chrome Web Store API |
| `CHROME_CLIENT_SECRET` | Same OAuth client |
| `CHROME_REFRESH_TOKEN` | Generated once via OAuth flow ([guide](https://github.com/fregante/chrome-webstore-upload-keys)) |
| `AMO_JWT_ISSUER` | https://addons.mozilla.org/developers/addon/api/key/ |
| `AMO_JWT_SECRET` | Same page |

### Manual deploy from local machine

```bash
# Chrome
CHROME_EXTENSION_ID=... CHROME_CLIENT_ID=... CHROME_CLIENT_SECRET=... CHROME_REFRESH_TOKEN=... \
  npm run deploy:chrome

# Firefox
AMO_JWT_ISSUER=... AMO_JWT_SECRET=... npm run deploy:firefox

# Both
npm run deploy
```

Optional flags via env: `CHROME_SKIP_PUBLISH=1` (draft only), `CHROME_TRUSTED_TESTERS=1`, `AMO_CHANNEL=unlisted`.

## Code Style Guidelines

### Language & Approach
- **Vanilla JavaScript** (ES6+) — no frameworks, no TypeScript
- **Strict mode**: All code runs in an IIFE with `'use strict'`
- **Browser APIs only**: DOM APIs, MutationObserver, localStorage, sessionStorage
- **Basecamp integration**: Targets Basecamp 4's DOM structure and Turbo events

### Code Organization
- **Section headers**: Use ASCII art separators for major sections within a file:
  ```javascript
  // ──────────────────────────────────────────────
  // Section name
  // ──────────────────────────────────────────────
  ```
- **Module files**: Logic is split across focused ES module files under `shared/` (see Project Structure above)
- **Entry point**: `shared/content.js` imports from all modules and wires up init + Turbo events
- **Dependency direction**: `content.js` → `filters/` → `ui/`, `data/` → `utils/` → (no imports)

### Naming Conventions
- **Constants**: `SCREAMING_SNAKE_CASE` (e.g., `LOG_PREFIX`, `FILTER_BAR_ID`, `TAG_REGEX`)
- **Functions**: `camelCase`, descriptive verbs (e.g., `renderTagPills`, `extractTags`, `scanPersons`)
- **Variables**: `camelCase` (e.g., `tagCounts`, `assigneeMap`, `authorMap`)
- **CSS classes**: BEM-style with `bkf-` prefix (e.g., `bkf-filter-bar`, `bkf-dropdown__menu`, `bkf-tag-pill`)
- **Data attributes**: `data-bkf-*` (e.g., `data-bkf-tags`)
- **DOM IDs**: Kebab-case with `bkf-` prefix (e.g., `bkf-assignee`, `bkf-author`, `bkf-tag`)

### Functions
- **JSDoc comments**: Add doc comments for complex functions
  ```javascript
  /**
   * Extract all tags from a text string. Returns array of normalized tag strings.
   */
  function extractTags(text) { ... }
  ```
- **Pure functions**: Prefer pure functions for data transformations
- **Return early**: Use early returns to reduce nesting

### Error Handling
- **Logging**: Use custom logging functions with prefix
  ```javascript
  const LOG_PREFIX = '[BKF]';
  const log = (...args) => console.log(LOG_PREFIX, ...args);
  const warn = (...args) => console.warn(LOG_PREFIX, ...args);
  ```
- **Null checks**: Always check for element existence before manipulation
- **No try-catch**: Code relies on null checks rather than exception handling

### CSS
- **BEM naming**: Block-Element-Modifier with `bkf-` prefix
- **Basecamp matching**: Match Basecamp's visual style (colors, fonts, spacing)
- **z-index layering**: filter bar: 10, dropdown: 999

## Testing

### Manual Testing Workflow
1. Edit any file under `shared/` (entry point, modules, or CSS)
2. The watcher (`npm run dev`) rebuilds automatically
3. Reload the extension in Chrome (`chrome://extensions` → ↺)
4. Navigate to a Basecamp card table: `https://3.basecamp.com/*/buckets/*/card_tables/*`
5. Check browser console for `[BKF]` log messages

### Test Scenarios
- **Filter dropdowns**: Select assignee/author/tag filters, verify cards hide/show
- **Tag pills**: Verify tags render on cards, detail pages, and in edit mode
- **Tag editor**: Add/remove tags using the picker in edit mode
- **Column counts**: Verify counts update when filtering (e.g., "(5/12)")
- **Turbo navigation**: Navigate between pages, verify filters persist/reset correctly
- **Edge cases**: Empty boards, unassigned cards, cards with no tags

### Agent Testing (Browser Console Injection)

AI agents with browser access can test changes without reloading the extension by injecting code directly via the console. Since `content.js` is minified in production builds, use `npm run build -- --dev` first for readable output.

#### Inject JS (from the bundled `chrome/shared/content.js`)
```javascript
// Run in browser console on a Basecamp card table page
// (paste the contents of chrome/shared/content.js — the esbuild output, not the source)
```

#### Inject CSS
```javascript
document.getElementById('bkf-injected-styles')?.remove();
const s = document.createElement('style');
s.id = 'bkf-injected-styles';
s.textContent = `/* contents of shared/content.css */`;
document.head.appendChild(s);
```

**Note**: since `content.js` runs in an IIFE, re-executing it accumulates event listeners. Reload the page between full injection tests.

## Browser Compatibility

- **Chrome**: Manifest v3, tested on Chrome 120+
- **Firefox**: Manifest v3, tested on Firefox 109+
- **Safari**: Safari Web Extension, tested on Safari 17+
- **Target**: Basecamp 4 only (`https://3.basecamp.com`)

## Key Constraints

- Vanilla JS only — no TypeScript, no framework
- esbuild bundles all modules into one output IIFE (`bundle: true`, `format: 'iife'`)
- Must not break Basecamp's native functionality
- Must handle Turbo navigation (SPA-style page loads)
- Must be visually consistent with Basecamp's design system
- Must persist filter state across navigations (localStorage + URL hash)
